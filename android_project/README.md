# Family Finance Tracker (Android)

Production-ready Android app for family finance tracking.

- **Package:** `com.timmat.financetracker`
- **Stack:** Kotlin, Jetpack Compose, MVVM, Hilt, Firebase (Auth + Firestore), StateFlow
- **Auth:** Google Sign-In (Firebase Auth) via Credential Manager
- **Backend:** Firebase only (no custom backend)

## 2. Firebase setup (already done, verify these)

The project assumes `app/google-services.json` is present for package `com.timmat.financetracker`.

### Required Firebase services
1. **Authentication → Sign-in method → Google** (ENABLED)
2. **Cloud Firestore** (created, in *Native* mode, region of your choice)
3. **Firestore → Rules** → paste contents of `firestore.rules` and **Publish**
4. **Firestore → Indexes** → import `firestore.indexes.json` (or create manually as listed below)

### Google Sign-In Web Client ID
Google Sign-In on Android requires the **Web client (OAuth 2.0) ID** generated by Firebase (not the Android client ID).

1. Open Firebase Console → Project Settings → your Android app → `google-services.json` already contains the `oauth_client` entries.
2. The app reads the Web client ID automatically via `R.string.default_web_client_id` (generated at build time from `google-services.json` by the `com.google.gms.google-services` Gradle plugin). No manual steps needed.

### SHA-1 (required for Google Sign-In)
Add your debug and release SHA-1 fingerprints to the Android app in Firebase Console:

```bash
# Debug
./gradlew signingReport
# → copy the SHA1 from the "debug" variant and paste it in Firebase Console
# → then RE-DOWNLOAD google-services.json and replace app/google-services.json
```

## 4. Firestore data model

See **section 6** below and `firestore.rules` for exact access rules.

### Collections
| Collection      | Doc ID                | Notes                                           |
|-----------------|-----------------------|-------------------------------------------------|
| `users`         | `{uid}`               | uid, email, displayName                         |
| `families`      | auto                  | name, createdBy, memberIds[] (denormalised)     |
| `familyMembers` | auto                  | userId, familyId, role (`admin`|`member`)       |
| `invitations`   | auto                  | email (lowercased), familyId, status            |
| `categories`    | auto                  | name, familyId                                  |
| `transactions`  | auto                  | familyId, userId, amount, type, categoryId, date, recurrence |
| `budgets`       | auto                  | familyId, categoryId, monthlyLimit              |

`memberIds[]` is stored on the `families` doc so security rules can verify membership in O(1) without extra reads. It is kept consistent by the repository when users join/leave.

### Composite indexes (see `firestore.indexes.json`)
- `transactions`: `familyId ASC, date DESC`
- `transactions`: `familyId ASC, categoryId ASC, date DESC`
- `budgets`: `familyId ASC, categoryId ASC`
- `familyMembers`: `userId ASC, familyId ASC`
- `invitations`: `email ASC, status ASC`

## 5. Setup verification

After building & installing:

1. **Launch app** → Login screen appears.
2. **Tap "Continue with Google"** → Credential Manager sheet shows your Google accounts. Pick one.
3. App navigates to **Onboarding**. Because you have no families yet, you see two options:
   * **Create family** (default) → enter a name → you become the `admin` of a new family with 8 seeded default categories.
   * **Join with code** → paste the 6-digit code you received by email (sent by an admin of the family that invited you).
4. **Dashboard** shows current month's income total, expense total, and per-category budget usage. An admin sees the "Family" entry in the top bar.
5. **Add a transaction** → it appears in the list and updates totals.
6. **Invite flow (admin):**
   * Open **Family** → type an email → **Generate invitation code**.
   * The app creates an invitation doc whose ID *is* the 6-digit code, and displays it prominently.
   * Email/share that code with the invitee (out of band — the app doesn't send email itself).
   * The invitee signs in on another device → Onboarding → **Join with code** → pastes the code → joins as a `member`.

### Verifying Firestore rules work
- From Firebase Console → Firestore → **Rules Playground**, simulate:
  - `get /families/{familyId}` with a user NOT in `memberIds` → **denied**
  - `create /categories/{id}` with role `member` → **denied**
  - `create /categories/{id}` with role `admin` → **allowed**
  - `create /invitations/12ab34` (non-numeric ID) → **denied** (code regex fails)
  - `update /invitations/{pendingCode}` flipping status to `accepted` as any signed-in user → **allowed** (possession of the code is the authorisation)
  - `update /families/{familyId}` as non-admin, adding only your own uid to memberIds → **allowed** (self-join path)
  - `update /families/{familyId}` as non-admin, adding another user's uid → **denied**

### Why `createFamily()` uses two commits
Firestore evaluates rules for each write in a batch against the **pre-batch** database state. If we tried to write family + admin-member + categories in one batch, the category writes would be rejected because `isAdminOf()` can't see the not-yet-written member doc. Committing the member doc first makes subsequent admin-only writes pass. See `FamilyRepository.createFamily()` for the implementation.
